# 2.12 Mono Heap Memory

## 2.12.1 Brief Principle

For game projects, in addition to memory occupation caused by the common resources mentioned above, another major part comes from code-related allocation.

**Mono Heap Memory** is the core memory area for Unity C# script runtime, mainly used for dynamic allocation and management of managed objects (such as string, List, custom class instances, delegates, etc.).

Besides high resident memory increasing the risk of crashes like other memory issues, unreasonable heap allocation also directly affects GC (Garbage Collection) time and frame stability, which requires equal attention.

Mechanically, Unity uses a **generational garbage collection mechanism** to manage the Mono heap. The core logic can be divided into three steps:

**Object Allocation**: Reference-type objects created by `new`, value-type boxing, string concatenation, and other operations in C# all apply for memory space from the Mono heap. The heap is managed as continuous blocks, with new objects preferentially allocated in free areas.

**Heap Expansion**: When free space is insufficient, Unity does not trigger GC immediately, but requests the system to expand the heap (default expansion: 50%~100% of current size) until reaching the device memory limit.

**Garbage Collection**: When heap usage reaches a threshold or `GC.Collect()` is called manually, GC traverses all managed objects, marks unreferenced objects, and releases their memory after about 6 consecutive unreferenced GC cycles. The reclaimed space is returned to the heap’s free list for reuse.

This leads to three common issues in heap memory analysis:

![43](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.12Mono/43.png)

(1) **Heap Composition**

As shown in the Memory Profiler screenshot, **Reserved Mono** is actually divided into three parts:

- Reserved space
- Actual object usage (Objects)
- Empty Fragmented Heap Space

Only the **actual object usage** is controllable by developers. From the expansion mechanism above, the larger this base value, the larger the reserved space. Therefore, optimizing actual object usage reduces memory more significantly than surface numbers suggest.

(2) **Heap Fragmentation**

Frequent allocation and release during gameplay easily cause fragmentation: large objects released, then small objects allocated immediately.

In projects with frequent allocations, GameOptim often observes that object usage and fragmentation gradually become equal.

Fragmentation growth can only be slowed by **avoiding frequent interleaved allocation/release of large and small objects**. Reducing actual object usage remains the primary optimization target.

(3) **The Myth: “Mono Heap Only Grows, Never Shrinks”**

Developers often ask: Why does the Reserved Mono curve rise and fall in test reports if the heap only grows?

In fact:

GC-reclaimed free memory is kept in the heap for reuse. If free space is long-term excessive, Unity **actively returns surplus memory to the system** at specific times (low-memory warning, scene switch), causing heap contraction.

In short: **physical memory pages are returned; only the address space only increases**.

## 2.12.2 Continuous / Peak Allocation Stacks

On the heap allocation details page, you can inspect the specific call stacks of high-allocation functions. We focus on two types:

**One-time excessive heap allocation**:

Peaks usually appear during initial table loading. Developers must verify rationality based on stack info. Peaks during runtime require special attention.

![46](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.12Mono/46.png)

**Continuous high heap allocation**:

Frequent allocation every frame or every few frames leads to higher GC frequency and frequent stutters. Use call stacks to identify which component is allocating continuously.

![47](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.12Mono/47.png)

## 2.12.3 Leak Analysis

On the leak analysis page, check heap residency for each function.

Select two sampling frames in the chart for comparison to view changes in heap residency and identify which stacks cause rising memory.

![48](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.12Mono/48.png)

This helps:

- Avoid memory leak risks from continuously rising heap
- Optimize high-residency functions for timely release, reducing single GC duration

It is recommended to run **GOT Online Mono Mode tests for at least 1 hour**; otherwise, leaks are often not exposed.
