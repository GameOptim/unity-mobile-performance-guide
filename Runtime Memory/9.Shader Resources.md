# 2.9 Shader Resources

## 2.9.1 ShaderLab

Unity 2019.4.20 marks a turning point in Shader memory statistics. Before this version, Shader memory was mainly counted under **ShaderLab**; after this version, it is mainly counted under the Shader resource itself.

For projects using Unity versions earlier than 2019.4.20, ShaderLab memory usage can be viewed in Memory Profiler snapshots.

Whether the Shader resource itself or ShaderLab has excessive memory usage, optimization should focus on controlling **Shader count, variant count, and Shader complexity**.

## 2.9.2 Variant Count and Complexity

For a single Shader resource, high memory usage essentially comes from a high compiled instruction count. This can be understood as a product of two factors:

**variant count** and **average instruction count per variant (i.e., Shader complexity)**.

Excessive variants are the main cause of large Shader memory and package size, and are relatively easy to detect and fix.

During project iteration, unused or deprecated keywords may remain, causing exponential variant growth.

Some Shaders are written with complex keyword combinations that are never used, resulting in redundant variants.

The Local Resource Detection tool provides Shader detection to view variant counts and locate Shaders with excessive variants.

![38](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.9Shader/38.png)

To address this, Unity provides callback functions to strip unused keywords or keyword combinations during AB packaging or build.

For variant stripping methods, refer to the Unity documentation: *Stripping scriptable Shader variants*.

Shader complexity also relates to GPU performance optimization, which is discussed in detail in the later GPU chapter.

## 2.9.3 Redundancy

Shader redundancy requires special attention. It not only increases memory usage but may also cause repeated parsing, leading to unnecessary runtime overhead from `Shader.Parse` and `Shader.CreateGPUProgram`.

A common practice is to use **ShaderVariantCollection** (a built-in Unity type) to collect all variants used during rendering.

Bundle it together with Shader dependencies, then load, cache, and warm up the collection uniformly at runtime.

This consolidates the overhead of `Shader.CreateGPUProgram` during early loading or scene switching, avoiding stutters caused by on-demand Shader compilation during combat.

![39](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.9Shader/39.png)

Another benefit of variant collection is identifying unused keyword combinations or variants, which can then be stripped via callbacks, effectively controlling overall Shader memory.

Generally, with well-managed complexity and variant count, no redundancy, and most unused variants stripped, even mobile projects with heavy PBR Shaders and high visual requirements can keep Shader memory within **50–60 MB**, which is acceptable for caching.

The above mainly applies to custom Shaders.

Built-in Shaders are recommended to be added to **Project Settings → Graphics → Always Include Shaders** to prevent redundancy.

Conversely, custom Shaders should **not** be added there to avoid redundancy.

## 2.9.4 Standard Shader

`Standard` and `ParticleSystem/Standard Unlit` often appear in the resource list.

These two Shaders have huge variant counts, very high loading overhead, and large memory usage. Direct use in projects is **not recommended**.

They usually appear because imported FBX models or Unity-generated objects use the default material, which depends on the Standard Shader. Detection and cleanup are recommended.

The online AssetBundle detection tool can be used to locate which ABs and resources reference these Shaders.

If Standard or Standard Unlit must be used, it is better to rewrite a custom Shader containing only required variants.

![40](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.9Shader/40.png)

## 2.9.5 Detecting Shader Issues with Local Resource Detection

Local Resource Detection includes the rules mentioned earlier:

- Shaders with excessive global keywords
- Shaders likely to generate excessive variants
- Shaders with excessive variants after build
- Materials using Standard Shader

These rules help developers accurately locate Shader resources with potential performance risks.
