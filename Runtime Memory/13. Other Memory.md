# 2.13 Other Memory

After optimizing the **Reserved Total** memory allocated by Unity, we still cannot be careless.

In normal cases, the **PSS Total** value mentioned earlier is **200–300 MB higher than Reserved Total**, which can be considered acceptable.

However, some projects show a gap of **500–600 MB or even more**.

## 2.13.1 Lua Memory

**GOT Online Lua Mode** provides performance profiling for the Lua scripting language.

The function name format is:

**FunctionName@FileName:LineNumber**

You can locate CPU bottleneck functions and peak time causes using the Lua filename, line number, and function name provided in the report.

The Lua function format is **X@Y:Z**, where:

- X: function name (defaults to `unknown` if unavailable)
- Y: file path where the function is defined
- Z: line number where the function is defined

Note: When Lua runs as bytecode, Z is always **0**. Therefore, it is recommended to use **Lua source code** during testing as much as possible.

For memory allocated by Lua, the report samples values every 30 frames in the line charts of **Total Heap Memory** and **Lua Memory Peak**.

The trend helps developers understand heap allocation during runtime.

A drop in heap memory indicates a **GC occurred**.

Frequent GC lowers the Lua memory peak but introduces extra CPU overhead.

The specific impact of the Lua GC mechanism and strategy on memory will be discussed in detail later.

As shown in the example curve below, Lua memory in this project shows a significant upward trend during the test.

Fortunately, the total base is small.

If memory rose, for example, from **70 MB to 120 MB**, serious **Lua memory leak risks** would require urgent attention.

You may also notice statistics for **Table, Function, Userdata** on the total heap page, which provide auxiliary information.

While overall memory trends can be seen from the curve, counting specific data structures serves two purposes:

- Identify which structure has a matching upward trend, indicating it may be the main cause of memory growth.
- Watch for abnormally high counts. For example, most projects have **100,000–200,000 Tables**, but some reach **800,000–900,000**, indicating large optimization potential.

The detailed memory allocation view in Lua Mode is **similar to the Mono Mode report**.

Another important function in the Lua Mode report is **Mono Object Reference Statistics**.

## 2.13.2 Lua GC

For automatic memory management in modern languages, there are two mainstream mechanisms:

**Reference Counting** and **Mark-and-Sweep**.

Lua uses GC based on **mark-and-sweep**.

For dynamic languages, reference counting introduces excessive overhead — even programs with no allocation still pay the cost.

The Lua garbage collector itself does **not** handle low-level memory allocation; this is done by an external allocator injected when creating the Lua VM.

All objects created by the VM are linked in a global list.

Objects indirectly reachable from the **VM root set** are preserved; others are collected at an appropriate time.

The root set includes the registry, native metatables, global tables, main thread, standard library code, etc.

In short: Lua scans and marks unreferenced objects and reclaims them.

Before Lua 5.0, a simple **mark-and-sweep** was used:

1. Traverse from roots and mark live objects.
2. Iterate the full object list and delete unmarked objects.

From **Lua 5.1 onward**, an **incremental GC** with **tri-color marking** was introduced:

- **White**: unreachable (to be collected)
- **Gray**: reachable but not fully scanned
- **Black**: fully scanned and safe

Invariants maintained at all times:

1. All root-referenced objects are black or gray.
2. Black objects never point to white objects.
3. White objects will be collected; black objects preserved; gray objects need further traversal.

GC completes when **no gray objects remain**.

### When Does Lua GC Run?

Incremental GC is **not time-based** — it runs **only when the VM allocates new memory**.

GC workload is determined by:

- New memory allocated
- Memory marked or swept

Too much work per step causes stutters; too little leads to slow reclamation.

For full GC (Lua 5.0), GC triggers when memory doubles.

From 5.1 onward:

- **LUA_GCSETPAUSE**: controls how much memory grows before next GC (default = 2)
- **LUA_GCSETSTEPMUL**: controls GC speed (default = 2, meaning GC runs at twice the allocation speed)

The value **2** is empirical, usually ensuring collection outpaces allocation.

Example (default settings):

After GC, memory is 100 MB.

Lua waits until memory reaches **200 MB** to GC again.

This default behavior is risky.

If GC frequency is too low and Lua memory peaks are too high, **lower LUA_GCSETPAUSE to increase GC frequency**.

## 2.13.3 Lua References to Mono Objects

When using Lua for game development, you frequently access **Unity / C# objects**.

When you call `Object.Instantiate` in Lua:

- The Lua layer auto-generates **Wrapper code** for each class.
- All Unity interfaces are wrapped and registered into Lua.

When calling functions from Lua, the Lua state is passed into wrappers, allowing parameter type and overload matching.

After `Object.Instantiate`, the returned object enters the Unity Scene and gains a native reference.

However:

If a Lua-created object has **no C# references**, it will be collected by C# GC when the function returns — even if you still need it in Lua.

Thus:

**The Lua layer manages the object lifecycle, and C# must hold a reference to prevent early collection.**

To achieve this, a **Push** operation stores the object in a C# container.

But this creates a new risk:

**C# does not know when to release the reference, causing Mono heap memory leaks.**

These references can only be released when Lua GC collects the corresponding **Userdata**.

**GOT Online Lua Mode** allows analysis via the **Mono Reference Object Statistics** page.

Since GC is triggered manually during sampling, objects still counted are **not released by Lua and cannot be reclaimed in the short term**.

Their count should not be excessively high.

The key metric is **Destroyed Object Count**:

These are objects **already destroyed in the scene but still held in C# containers**, occupying Mono heap memory.

A rising trend indicates a **Mono heap leak**, requiring combined analysis with the GOT Online Mono report.

The solution is to **find reference chains in Lua and release objects promptly**.

![50](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/2.13OtherMemory/50.png)

In the Mono object reference bar chart provided by GameOptim:

- **Black**: non-destroyed objects
- Gray/other: destroyed objects still referenced by Lua

If the **destroyed count keeps rising continuously**, serious memory leaks exist and require immediate attention.



## 2.13.4 Lua Config Table Optimization

Besides business logic, Lua is also widely used for **data storage** (configuration files).

Configurations are originally maintained by designers in Excel, then exported to Lua source files via tools for direct use in the game.

These files store Excel-equivalent data in Lua tables.

A config table can be regarded as a **2D array**:

one key (first column) corresponds to one row of sub-data, so the full configuration is a large table containing many small tables.

Large or redundant configs lead to oversized Lua files, **seriously increasing load time and memory usage**.

Common redundancy causes:

1. Many duplicate values or meaningless nulls (0, empty tables, etc.)
2. Many Chinese strings requiring later localization
3. Many identical complex sub-tables or arrays

**Optimization solutions**:

1. Treat the most frequent value in a column as the **default value**, remove it from the Lua table, and use the `metatable` mechanism for global default storage.
2. Replace Chinese strings with unique integer IDs and add lookup logic at read time.
3. **Deduplicate** identical sub-tables/arrays and replace them with references.

All operations are based on **deduplication**, so **the entire config table MUST be read-only**.

Otherwise, all optimizations are invalid.

This reduces readability: shared sub-tables are replaced with `local` variables.

Due to Lua limitations, **maximum local variables per scope = 200** (defined in lparser.c: `#define MAXVARS 200`).

Excess tables are stored in a temporary array, causing slight extra lookup overhead — acceptable in practice.

## 2.13.5 Native Heap Optimization

As discussed in Chapter 2.1, if `adb dumpsys meminfo` shows **continuously rising Native Heap** and third-party plugins / Lua are not the cause,

**Perfetto** is the core tool for locating native heap allocation and leaks, especially for:

- IL2CPP builds
- Unity engine internal issues
- Custom C++ plugin memory anomalies

Perfetto is based on Android’s `heapprofd`, samples `malloc/free` callstacks, and displays allocation sources via flame graphs.

It fills the gap of Unity Memory Profiler, which **cannot track Native Heap in Untracked memory**.

### Prerequisites

- Android 10 or above
- Non-userdebug devices: set APK to `debuggable` or `profileable`
- Perfetto package + Python environment
- ADB connection to the device and game process

### Collection Steps

1. Launch the game, enter the abnormal memory scene, get package name / PID via `adb shell ps`.

2. Start heap sampling:

   ```
   python perfetto/tools/heap_profile -n PACKAGE_NAME
   ```

3. Reproduce memory growth (scene switching, resource loading, core gameplay).

   Manually trigger snapshots:

   ```
   adb shell killall -USR1 heapprofd
   ```

4. Stop tracing, export `raw-trace` file, analyze online at: ui.perfetto.dev

   

### Result Analysis

Key views:

- **Unreleased Malloc Size**: locate persistent allocations
- **Total Malloc Size**: check frequent allocation/free and fragmentation

**Flame graph**:

Block width = memory size; top-to-bottom = call chain.

Focus on:

- IL2CPP
- Unity engine modules (Rendering, Audio)
- Custom C++ plugins

Continuous unreleased growth = **leak or unreasonable residency**.

**Symbolization**:

If callstacks show raw addresses:

- Build with IL2CPP Debuggable
- Configure `llvm-symbolizer` and symbol files to map addresses to function names.

### Common Issues & Optimization

- **Engine leaks**: Unity native modules (e.g., AssetBundle serialization). Check caching logic.

- **External C++**: Lua, HybridCLR, custom code. Locate via allocation/constructor functions.

- **Render thread / Graphics API**:

  - Shader GPUProgram generation
  - Render buffers
  - Engine settings

  

## 2.13.6 .so mmap Optimization

`.so mmap` is the **memory mapping of shared libraries** on Android, a major part of **Untracked Memory**.

In games, it mainly includes:

`libunity.so`, `libil2cpp.so`, plugin and third-party SDK `.so` files.

Excessively large `.so mmap` (especially on low-end devices) squeezes memory and **increases OOM crash risk**.

Check via:

```
adb shell dumpsys meminfo PACKAGE_NAME
```

Warning thresholds:

- `.so mmap` PSS > **10% total device memory**
- or > **200 MB**

To identify large libraries:

1. **Static analysis**: Unpack APK, check size and count of `.so` files in `/lib`.

2. **Runtime mapping**:

   ```
   adb shell cat /proc/PID/maps
   ```

   Check for unused, duplicated, or unloaded `so.` files.

### Optimization

- Keep only mainstream ABIs (e.g., `arm64-v8a` for China)
- Delete abandoned SDKs and debug `.so` files
- **Strip code** for `libil2cpp`:
  - Enable `Strip Engine Code` in Player Settings
  - Set stripping level to **High**
  - Remove unused Unity modules (AR, VR, Physics, etc.)
- Check Lua-related libraries (`liblua.so`) for excessive code size

Also avoid these causes of large `.so`:

1. Excessive use of C++ templates
2. Large amount of auto-generated code
3. Excessive Lua–C# wrapper code



## 2.13.7 Wwise Audio Memory Optimization

Wwise is a mainstream mobile audio plugin using **event-driven + SoundBank architecture**.

Its memory is **independent of Unity Native and Mono Heap**, and mostly appears in **system Native Heap** and **Unknown**.

Wwise memory has four parts:

1. **Metadata memory**: Allocated when loading Banks; contains Event, Switch, State, RTPC, mixer graph. Small but critical. Fully released when Bank is unloaded.
2. **Media memory**: Audio waveform (WEM) storage — **the largest part**.
3. **Engine runtime memory**: Playback instances, 3D spatialization, mixer buffers. Auto-managed.
4. **I/O & Streaming memory**: Stream buffers and async IO cache. Configurable per platform.

### Common Issues & Solutions

1. **Unreasonable Bank granularity**

   - Huge Banks: many unused audio objects resident in memory

   - Over-fragmented small Banks: high metadata & IO overhead

     Fix: Split Banks by scene/level; shared audio into `SharedBank`.

   

2. **Load/unload mismatch**

   Load-only, repeated load, cross-scene references → media memory leaks.

   Monitor with **Wwise Profiler**.

   

3. **Incorrect load mode**

   - Long BGM loaded fully → memory spike

   - Short frequent sounds streamed → stuttering

     Fix:

   - Long audio: **Streaming**

   - Short repeated audio: **Load into memory**

   

4. **Over-sized initialization settings**

   Default memory pool, voice count, path count, IO buffer too large.

   Use **tiered settings** for low-end devices.
