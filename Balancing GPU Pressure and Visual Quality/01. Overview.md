## 4.1 Overview

In recent years, several successful projects with high-quality graphics have intensified market competition, even crossing genre boundaries. More developers have realized that **excellent visual quality**, like attractive gameplay, has become indispensable for attracting and retaining players.

Accordingly, many teams have focused heavily on art production and rendering effects during development. However, this has led to serious problems: **rising rendering pressure**, especially insufficient understanding of rendering performance monitoring and maintenance, resulting in inefficient workflows and high late-stage correction costs.

Among these, **GPU pressure has surpassed CPU pressure** to become the primary performance bottleneck in many projects.

Yet GPU issues are closely tied to hardware: different manufacturers and chips behave differently, making device tiering and standard setting difficult.

Furthermore, Unity built-in tools rarely provide accurate GPU performance data, while hardware vendor tools are numerous, complex, and hard to use effectively. This creates great difficulty in diagnosing and optimizing GPU-related problems.

Thus, is there a **universal methodology** to determine:

- Whether a project is GPU-bound
- What type of GPU pressure exists
- How to resolve it

To fill this tool gap and meet growing GPU optimization demands, **GameOptim launched the fifth major mode of GOT Online in late 2023: the GPU Mode**, dedicated to GPU performance. It aims to support all mobile hardware and provide actionable parameters for real-world optimization.

Before explaining how GPU Mode analyzes performance, we first review the per-frame rendering pipeline on mobile:

- The **CPU** handles the application stage.
- The **GPU** handles the geometry stage and rasterization stage.

For most projects with **multithreaded rendering enabled**:

The main thread performs DrawCall preparation, culling, etc. A separate **render thread** handles high-cost work: submitting textures and DrawCalls to the GPU, and waiting for GPU completion.

In heavy rendering scenes, the Timeline often shows:

The main thread **must wait for the render thread to finish the previous frame** before starting the current frame’s rendering. During this time, the render thread is mainly submitting DrawCalls and waiting for the GPU.

- `Gfx.WaitForPresentOnGfxThread` (main thread): marker waiting for the render thread.
- `Gfx.PresentFrame` (render thread): marker waiting for the GPU.

These are **not actual time costs**, but synchronization markers between CPU, render thread, and GPU.

![](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.1Overview/81.png)

The performance profile in the figure shows a **typical GPU-bound scenario**.

CPU pressure is low: total module time < 33 ms (target for 30 FPS), but the GPU is so overloaded that the game only runs at ~10 FPS.

**Conventional CPU optimization will have no effect.**

Example:

- CPU time: 30 ms; GPU wait: 80 ms; synchronization marker shows 50 ms.
- After optimizing CPU to 20 ms, frame rate **does not increase** — synchronization wait becomes 60 ms.

Conversely, if CPU time is 80 ms, no GPU wait markers appear, but **GPU pressure may still exist but be masked by the CPU bottleneck**.

This simple **barrel effect** has become widespread in mobile projects analyzed by GameOptim, which is why we state:

**GPU pressure has surpassed CPU pressure as the main performance bottleneck in many projects.**

At this point, we can roughly judge whether a project is GPU-bound on the test device.

However, `Gfx.WaitForPresentOnGfxThread` is **only a synchronization marker**, affected by CPU load and unable to accurately compare GPU pressure between scenes. It also cannot guide specific GPU optimization or tiering.

What about **GPU Time** from other profilers?

GameOptim tests show:

- Identical APK and test 流程 often result in **higher GPU Time on better GPUs**.
- In an empty scene with no pressure locked at 30 FPS, GPU Time may still show 33 ms.

This inconsistency arises because:

- GPU Time calculation varies across SoCs.
- Under no load or high CPU load, the GPU may **downclock to save power** even if running at high frequency.

In short, **GPU Time is unreliable**.

Therefore, we must break free from engine-level concepts and return to the source to find a parameter that **truly reflects GPU rendering computation load**.

This parameter is the core of GOT Online GPU Mode:

**GPU Clocks**

It is also the main topic of this chapter — explanation, analysis, and corresponding optimization suggestions.
