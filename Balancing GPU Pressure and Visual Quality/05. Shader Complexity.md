# 4.5 Shader Complexity

After discussing computation volume, we now address **computation complexity**.

For both vertex and fragment stages, complexity involves many factors, but the most adjustable and quantifiable part for developers is **shader complexity** in each stage, which directly contributes to **GPU Clocks**.

In the GPU Mode report, the **Shader Cycles** parameter shows the GPU cycles spent on shader processing, helping identify scenes with heavy shader pressure.

However, this value is also affected by total pixel count, so its reference value is limited.

In practice, developers prefer to directly observe and analyze **single shader complexity**.

The **Mali Offline Compiler** can output shader instruction count and cycle count.

It is recommended to prioritize shaders with **high screen coverage and high usage** to locate key optimization targets.

A common observation:

A **PBR shader** on character models may have very high complexity,

but contributes little to actual GPU time because **characters usually have small screen coverage and few pixels**.

The real bottleneck is often:

- Opaque objects with large screen coverage (terrain, architecture)
- Transparent objects with high Overdraw

Their shader complexity is slightly lower than characters, but **pixel count is far higher**, making them the main GPU burden.

Besides reducing pixel count, shaders also require **reasonable tiering and simplification**.

Example:

Particle shaders often use a **universal “uber shader”** for convenience.

In practice, most effects only use a few features, but the shader still runs unused code:

normal map sampling, lighting calculations, etc. — even when no texture is assigned.

This causes massive waste.

Solution:

Optimize via **keyword variants** or **split the shader into multiple lighter versions**.

Shader features that improve visuals but provide limited contribution should be **completely disabled on low-end devices**, using either **separate simplified shaders** or **Shader LOD**.
