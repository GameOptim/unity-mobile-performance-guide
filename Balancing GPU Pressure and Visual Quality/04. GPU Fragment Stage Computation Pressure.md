# 4.4 GPU Fragment Stage Computation Pressure

## 4.4.1 Render Resolution

For GPU pressure from the **fragment stage**, we also start with **computation amount**.

The computation amount in the fragment stage is determined by **total pixels rendered per frame**.

In the GPU Mode report, the **Fragment Shaded** parameter under GPU Shaded directly reflects this value.

It represents the total number of **Fragment Shader invocations per frame**, which is approximately equal to the total pixels rendered.

![85](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/85.png)

**Render resolution** defines the number of pixels required for one full-screen pass on a mobile device.

**Tiered render resolution control** is one of the most common and effective tiering strategies in mobile games.

According to GameOptim rendering analysis:

- Low-end devices: **0.7–0.8× native resolution**
- Mid-end devices: **0.8–0.9× native resolution**
- High-end devices: **1.0× full native resolution**

Some competitive games with high fluidity requirements but moderate visual demands even use **0.5× resolution**.

Example:

A device with native resolution **1080×1920** has about **2.0 million pixels** per full screen.

If scaled to **0.7× in both width and height**:

Total pixels = 0.7×0.7 = **0.49× original** (about 1.0 million pixels).

Fragment stage pressure (usually the main GPU cost) is **cut nearly in half**,

while the slight blur in 3D scenes is generally acceptable on mobile.

A common practical problem:

Many low-performance devices have **extremely high native resolutions** (long screens, 1080×2360 etc.).

A 1080×2360 screen has ~**2.5 million pixels** — **25% more** than 1080×1920, causing 25% higher fragment pressure.

A more reasonable approach:

**Set a fixed total pixel budget per tier**, not a simple fixed scale factor.

Calculate the native pixel count, then scale to fit the tier’s maximum affordable pixels.

Reducing render resolution is simple.

However, directly changing **Render Scale** also blurs UI, which is often unacceptable.

In URP projects, the recommended method:

- Use **Camera Stacking**
- Render the 3D scene to a **Render Texture (RT)**
- Display the RT via a **RawImage** under the UI camera

By adjusting only the RT resolution, you **reduce 3D GPU pressure without blurring the UI**.

Some teams modify pipeline code to set separate resolutions for scene and UI cameras.

## 4.4.2 Overdraw

Once we define the pixels per full-screen pass, the **average number of layers per pixel — Overdraw** is equally important.

In GPU Mode:

**Total Overdraw (simulated)** = Fragment Shaded / (1080×1920 standard 1080p pixels)

This shows the overall Overdraw trend during testing.

![86](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/86.png)

First, understand the sources of Overdraw:

In Unity:

- RenderQueue **< 2500**: opaque objects, rendered **front-to-back**
- RenderQueue **> 2500**: transparent objects, rendered **back-to-front**

For opaque objects with proper sorting, **depth testing** discards occluded pixels before fragment shading, greatly reducing Overdraw.

Ideally, opaque Overdraw should be **~1.0**.

The **main cause of high Overdraw** is almost always **transparent objects**:

**particle systems and UI**.

Overdraw from these can be analyzed in detail using GPU Mode’s **Overdraw Snapshot** feature.

Click **Dump** during testing; the report will show:

- Overdraw value per camera
- Captured frame image
- Camera-based Overdraw heatmap

In the heatmap:

**Brighter = more times the pixel is overdrawn**.

This allows you to:

- Identify which objects cause high Overdraw
- Find wasteful rendering with minimal visual contribution

![87](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/87.png)

![88](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/88.png)

In addition to visible objects, some Fragment Shaded cost comes from **off-screen rendering passes**:

post-processing sampling, Copy operations, **Blit** operations, etc.

These effectively redraw the full screen and add Overdraw.

This appears as:

**Total Overdraw (simulated) > sum of camera Overdraws in snapshot**

indicating high Overdraw from pipeline passes.

## 4.4.2.1 Improper Render Order

If distant opaque objects are rendered **before** closer overlapping objects,

occluded pixels are drawn twice, causing Overdraw.

This often happens with **terrain**.

When opaque objects share the same Render Queue, Unity renders closer objects first.

But terrain has parts both near and far, leading to bad sorting.

Solution:

Adjust **Render Queue** so that **closer objects (characters, props) render first**, terrain last.

On mobile, **Early‑Z** performs depth test **before fragment shading**,

skipping computation for occluded pixels.

Note:

Render order optimization is most effective on **low-end devices without HSR**.

Newer devices with **HSR (Hidden Surface Removal)** are less affected.

## 4.4.2.2 Particle Systems

GameOptim tools can accurately locate high-cost particles.

Method 1:

Create an empty test scene, play all project particles sequentially,

test with GameOptim SDK, and analyze GPU Clocks / Fragment Shaded / Overdraw in GPU Mode.

Method 2:

Use GameOptim **local resource detection** to directly get a list of particles predicted to cause high Overdraw.

![89](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/89.png)

After identifying problematic particles:

**Simplify them drastically on low-end devices** to reduce fragment pressure.

Specific methods:

(1) Keep only **critical particle layers** on mid-low-end devices.

For a flame effect: keep only the core flame; disable smoke, sparks, haze.

Tiered design was discussed earlier.

(2) Limit **Max Particles** on mid-low-end devices.

Before modification：

![90](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/90.png)

After limiting the Max Particles to 10:

![91](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.4GPU_FragmentStage/91.png)

Also, if artists stack many overlapping particles for brightness:

Keep only 2–3 layers, but boost color/intensity in the material to achieve similar visuals.

(3) **Reduce particle screen coverage**.

Larger coverage = more overlap = higher Overdraw.

Common waste:

- Particles using large square textures with mostly fully transparent areas
- Gradient particles with big empty borders

These non‑contributing pixels are still fully shaded by the GPU.

**Crop textures** to remove transparent areas.

(4) Control particle **lifetime** and **Deactivate promptly**.

Some particles continue computing long after they visually contribute.

Shorten lifetime and disable explicitly.

(5) **Anim 帧烘焙 (Animation Frame Baking)**

For particles without complex 3D viewing or randomness,

baking to flipbook animation **extremely reduces Overdraw**.

A 10‑layer layered effect becomes **one single layer**, with a very simple shader.

This is widely used successfully in open‑world 3D mobile games.

(6) **Offscreen Particle Rendering**

Particles are one of the few effects that **do not become obviously blurry when resolution is reduced**.

You can render particles to a separate lower-res RT.

This introduces minor copy overhead but provides huge savings in projects with heavy particles.

Reference: *URP OffScreen Particle Render*.

## 4.4.2.3 UI

UI is another major source of transparent Overdraw.

(1) When a full‑screen UI is open, **disable UIs hidden behind it**.

(2) For UI elements with **Alpha = 0**,

enable **CullTransparent Mesh** on CanvasRenderer.

This preserves raycast input but skips rendering.

(3) **Minimize Mask components** — they increase Overdraw and DrawCalls.

Use **RectMask2D** instead for better performance.

(4) In URP:

Watch for unnecessary **Copy Color** / **Copy Depth** passes.

If UI and scene cameras share the same **RendererPipelineAsset**,

this causes redundant rendering and bandwidth waste.

**Recommendation**:

Use **separate RendererData** for UI camera and scene camera.
