# 4.3 GPU Vertex Stage Computation Pressure

We first discuss pressure from the **vertex stage**.

Fundamentally, GPU performance pressure in a stage equals **computation amount**, determined by two factors:

1. **Total number of units to process** (quantity)
2. **Average cost per unit** (computation complexity)

In the vertex stage:

- **Rendered triangle count** = quantity
- **Vertex Shader complexity** = complexity

Few developers modify vertex shaders directly, and diagnosis is similar to fragment shaders, so we cover both in later sections.

The **rendered triangle count** here refers to the **actual number processed by the GPU**,

which differs from “sum of triangles of models inside the view frustum”.

It depends on:

- Base mesh face count
- Culling results
- **Rendering passes**

Excessively high triangle count is reflected in **GPU Primitive** parameters:

- **Input Primitive**: Total primitives sent from CPU to GPU
- **Culled Primitive**: Primitives discarded in GPU stage (backface, frustum, tiny primitive culling, etc.)
- **Visible Primitives**: Primitives actually passed to the next stage (Input − Culled)

To reduce GPU computation:

**Input Primitive should be as small as possible, and Visible Primitive ratio as high as possible**.

![](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.3GPU_Vertex/83.png)

A reasonable ratio is roughly **50% visible, 50% culled**,

since faces toward/away from the camera are balanced in well-built scenes.

Ideally, invisible triangles should be **removed at mesh level**,

raising the visible ratio above 50% for higher efficiency. This is a common goal of mesh optimization tools.

However, many projects with vertex pressure show **70–80% culled primitives**, indicating massive waste.

Culled Primitive consists of three parts:

1. **XYPlane&FacingCullingPrimitives**: Backface culling + 2D frustum culling
2. **ZPlaneCullingPrimitives**: Depth frustum culling
3. **CoverageCullingPrimitives**: Tiny/sliver primitive culling

**Backface culling** is normal but should generally **not exceed 50%** of total primitives.

Higher ratios indicate poorly modeled objects or scene layout.

The other two types **should be very low** in ideal conditions.

Important distinction:

- **CPU frustum culling**: culls **entire objects** only if fully outside view.

  A large building/terrain is fully submitted to GPU even if only partially visible.

- **GPU frustum culling**: culls **per triangle**, resulting in massive wasted computation.

Thus:

**Split large, complex models into smaller pieces** and use SRP Batcher or runtime static batching.

Only visible parts are submitted to GPU.

**CoverageCullingPrimitives** (tiny face culling) is straightforward:

GPU discards triangles with extremely small screen size, high density, or extreme aspect ratio.

High values indicate **overly dense meshes for their screen size**.

This can be identified using the **mesh rendering density** metric mentioned in the memory chapter.

![](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/4.3GPU_Vertex/84.png)

The above data helps identify scenes with **primitive waste and large optimization space**.

For practical optimization, we must reduce total primitives to match hardware capabilities.

To achieve this, we use **Unity Frame Debugger** to analyze high vertex-pressure scenes identified by Triangle or Primitive curves.

Typical diagnosis workflow:

1. Use **Frame Debugger** to capture the frame.

2. Check **Triangle count** in the Stats panel.

3. Step through DrawCalls; observe how Triangle count changes.

   

   The cumulative count up to the selected DrawCall is shown.

4. Easily locate **which DrawCalls cause excessive triangles**.

You can also **enable/disable GameObject layers** to measure their contribution to triangle count.

For example: toggle the character root node to evaluate whether character polycount needs adjustment.

# After Locating Issues: Optimization Actions

Set **tiered triangle limits** based on GameOptim’s device-tier recommendations.

Example for very low-end devices:

- Total target: **150,000 triangles**
- Characters are priority: **100,000 triangles**
- Terrain/scene: **50,000 triangles**
- 5v5 combat → 10 characters total
- **Per character budget: 100,000 ÷ 10 = 10,000 triangles**

Optimize the following causes of high triangle count:

## (1) Level of Detail (LOD)

Especially effective for **open-world or long-view-distance scenes**, which suffer heavier vertex pressure.

Use **aggressive LODs** to reduce on-screen triangles.

## (2) Overly complex models

This is the **most common root cause**.

Often due to missing art standards early in development or only one set of high-poly assets.

Use **mesh rendering density** to filter problematic assets for efficient optimization.

## (3) CPU‑side culling

Reduce triangles **before sending to GPU**:

- Distance culling
- Size culling
- Layer-based culling

**Occlusion Culling** is risky:

Only effective when **many large objects are fully occluded**.

Otherwise, it often **reduces performance**.

Simple custom culling rules usually provide better cost-performance ratio.

## (4) Control rendering passes

Many features **double or triple triangle count**:

- Multiple light shadows
- Multi‑Pass Shaders
- Outline
- Reflections
- SSAO
- Multi‑camera rendering

These should be **selectively disabled on mid-low-end devices** via tiered settings.
