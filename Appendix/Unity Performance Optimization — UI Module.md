In the Unity engine, the mainstream UI frameworks include UGUI, NGUI, and the increasingly popular FairyGUI. This article mainly focuses on the most widely used UGUI for explanation. This article discusses UI optimization from the aspects of CPU time consumption, its impact on memory allocation, and its effect on GPU.

### I. CPU Time Consumption



**1.Canvas.SendWillRenderCanvases**
The time consumption of this function represents the update time caused by changes in the UI elements themselves, which can be understood as the time spent on UI updates. This should be distinguished from the time spent on mesh reconstruction in Canvas.BuildBatch (see below).

![1](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/1.png)

UI element updates include: replacing images, changes in text or color, etc. Displacement, rotation, or scaling of UI elements do not cause overhead in this function. The time consumption of this function depends on the number of UI elements being updated and their complexity. Therefore, to optimize the overhead of this function, you can typically focus on the following points:

**1) Reduce the frequency of updates for frequently changing UI elements**
For example, markers for monsters on the minimap, health bars for characters or monsters, etc., can be controlled so that the UI display is updated only when changes exceed a certain threshold. Similarly, skill cooldown effects, damage numbers, etc., can be updated every few frames.

**2) Try to avoid changes in complex UI elements**
For UI elements with a large number of vertices, such as Text with Rich Text, Outline, or Shadow effects, or Images with Image Type set to Tiled, updates can be highly time-consuming. If effects like Outline or Shadowmap are required but frequently change, such as floating damage numbers, consider using pre-rendered art text to avoid multiplying the vertex count by N times.

**3）Focus on Font.CacheFontForText**
This function often causes some performance spikes. The API mainly incurs overhead from generating dynamic font Font Texture. Sudden high runtime costs are likely due to writing many new characters at once, causing the Font Texture to expand. This performance issue can be optimized by reducing the number of font types, decreasing font sizes, and displaying common characters in advance to expand the dynamic font FontTexture.

![2](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/2.png)

**2.BuildBatch & EmitWorldScreenspaceCameraGeometry**
Canvas.BuildBatch is invoked when the merged mesh for UI elements needs to change. Typically, the previously mentioned calls to Canvas.SendWillRenderCanvases() will trigger Canvas.BuildBatch. Additionally, movement of UI elements within the Canvas can also lead to calls to Canvas.BuildBatch.

![3](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/3.png)

Canvas.BuildBatch initiates UI mesh merging on the main thread, with the specific merging process handled in a sub-thread. When the sub-thread is under excessive pressure or the UI mesh being merged is overly complex, waiting occurs on the main thread. The time spent waiting is recorded in EmitWorldScreenspaceCameraGeometry.

The high overhead generated by these two functions indicates that the Canvas undergoing reconstruction is very complex. In such cases, it is necessary to subdivide the Canvas. Typically, static elements should be placed in one Canvas, while UI elements that require updates should be placed in another. This way, the static Canvas, due to caching, will not undergo mesh updates, thereby reducing the complexity of mesh updates and decreasing the time spent on mesh reconstruction.

**3.SyncTransform**
It has been observed that in some projects, the CanvasRenderer.SyncTransform function is called frequently in certain frames. As shown in the example, the number of CanvasRenderer.SyncTransform calls reaches as high as 1,017. When Canvas.SyncTransform is triggered very frequently, it can cause its parent node, UGUI.Rendering.UpdateBatches, to incur significant performance overhead.

![4](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/4.png)

When the number of calls to this node is too high, consider the following four possibilities and adopt corresponding strategies to control the number of calls and reduce overhead:

1. Any change in the Transform information of a UI element (such as displacement, rotation, scaling, e.g., floating text animations) will cause the element itself to trigger CanvasRenderer.SyncTransform once. If many UI elements undergo Transform changes simultaneously, it will obviously lead to a high number of calls (e.g., frequently moving HUDs of other players in multiplayer games, damage number displacement animations that frequently bounce in combat scenes, etc.). In such cases, consider appropriately limiting or reducing the update frequency of these changes.
2. When calling SetActive(True) to activate a UI element, it triggers CanvasRenderer.SyncTransform for all UI elements under the current Canvas and its parent Canvas. Notably, calling SetActive(False) to hide a UI element does not trigger this. Therefore, it is advisable to separate frequently activated and hidden UI elements from other static elements.
3. When instantiating UI elements, it triggers CanvasRenderer.SyncTransform for all UI elements under the current Canvas and its parent Canvas.
4. When destroying UI elements using Destroy, it will only trigger CanvasRenderer.SyncTransform for all UI elements under the current Canvas. Considering points 3 and 4, it is advisable to separate frequently instantiated and destroyed UI elements from other static elements.

PS: When the above API does not actually take effect (e.g., calling SetActive(True) on an already activated object), CanvasRenderer.SyncTransform will not be triggered.



**4.EventSystem.Update**

1) High trigger call overhead

This function is triggered upon touch release. When the function itself incurs high CPU overhead, it is usually caused by calling other time-consuming functions. Therefore, further detection of the triggered logic is needed by adding Profiler.BeginSample/EndSample markers or using GOT Online service + GameOptim API markers.

![5](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/5.png)

![6](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/6.png)

2) High polling overhead

All UGUI components have the Raycast Target option enabled by default upon creation, essentially preparing them to receive event responses. However, in reality, most UI components such as Image and Text types do not participate in event responses. Nevertheless, they still engage in polling when the mouse/finger hovers or passes over them, simulating ray detection to determine whether the UI component is being hovered or passed over, resulting in unnecessary time consumption. Especially when there are many UI components in a project, disabling the Raycast Target setting for components that do not participate in event responses can effectively reduce the time spent in EventSystem.Update().

![7](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/7.png)

**5.UI DrawCall**
Typically, other modules in combat scenes have high time consumption pressure, so the UI module must carefully control performance overhead. Generally, it is best to keep UI DrawCalls in combat scenes around 40-50.

![8](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/8.png)

Without reducing UI elements, controlling the issue of DrawCalls essentially comes down to how to batch UI elements as much as possible. Generally, batching requires the same material, but in UI, it often happens that UI elements made with the same material and atlas cannot be batched. This is actually related to the calculation principle of UGUI DrawCalls. 



During the production process, it is recommended to pay attention to the following points:
(1) Only UI elements under the same Canvas can be batched together. Even if the Order in Layer is the same, UI elements from different Canvases will not be batched. Therefore, proper planning and production of UI are crucial.
(2) Try to integrate and create atlases as much as possible, so that the material atlases for different UI elements are consistent. UI elements like buttons and icons in the atlas, which require relatively small images, can be fully integrated and made into atlases. When they appear densely and simultaneously, this effectively reduces DrawCalls.
(3) Under the same Canvas and with consistent materials and atlases, avoid interleaving of layers. Generally speaking, ensure that UI elements meeting the batching conditions have the same "layer depth."
(4) Set the Pos Z of related UI elements to 0 as much as possible. UI elements with a Z value other than 0 can only attempt to batch with adjacent elements in the Hierarchy, making it easy to break batching.
(5) For Images with an Alpha of 0, make sure to check the Cull Transparent Mesh option on their CanvasRender component; otherwise, they will still generate DrawCalls and easily break batching.

### II. Memory

1. Typically, the heap memory allocated by UGUI itself is very minimal, so we need to focus on third-party plugins or custom UI components. For example, the popular UIParticles plugin, which facilitates convenient layer management between UI and special effects, initializes arrays based on the MaxParticles count of the ParticleSystem. Therefore, special attention should be paid to the MaxParticles count of the ParticleSystem.

   From the image below, it can be seen that the MeshImage UI component, written by the developer, generates a significant amount of heap memory and requires targeted optimization.

   ![9](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/9.png)

2) Merge atlases, and try to ensure that the same atlas does not contain more than 2 Atlases. Otherwise, loading any Sprite sub-image from this atlas into memory will cause all Atlases in this atlas to be loaded into memory.

3) GC Optimization for UGUI

   The GC optimization for UGUI has been discussed in detail in other articles. Here, I want to mention a point that is often overlooked: when a Prefab contains a large number of empty Text components, there will be significant GC Alloc during initialization. This is because, during initialization, the TextGenerator is initialized first. If the Text is empty, it will be initialized with a default capacity of 50 characters, meaning 50 UI Vertex and 50 UICharInfo. To avoid this, you can either ensure the Text is not empty or fill it with a space to prevent such allocations.



### III. GPU

1) When a full-screen UI is opened, it is recommended to close other UIs that are obscured by the background.



![10](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/10.png)



2) For UIs with an Alpha value of 0, it is advisable to check the "Cull Transparent Mesh" option on the Canvas Renderer component. This ensures that UI events are still responsive while avoiding unnecessary rendering.



![11](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/11.png)



3) Minimize the use of Mask components as much as possible, as they not only increase rendering overhead but also lead to a rise in DrawCalls. In cases of high Overdraw, consider using RectMask2D as an alternative.
4) Under URP, extra attention should be paid to the presence of unnecessary Copy Color or Copy Depth operations. This is particularly common when the UI and in-game cameras share the same RendererPipelineAsset, which can result in unnecessary rendering time and bandwidth waste, imposing additional GPU overhead. It is generally recommended to use different RendererData for UI cameras and scene cameras.

The above are some key issues and corresponding solutions to consider when optimizing the performance of the UI module. It is essential to tailor these approaches to the specific circumstances of your project. Additionally, leveraging GameOptim performance optimization services, such as real-device testing or GOT Online, can help quickly identify performance bottlenecks and ensure the smooth operation of your project.
