# 3.2 Rendering Module

For more comprehensive content on rendering module optimization, please refer to *Unity Performance Optimization Series — Rendering Module*.

## 3.2.1 Multithreaded Rendering

In single-threaded rendering, during each frame, the main thread (CPU1) first executes `Update`, performing a large amount of logic such as game AI, collision detection, and animation updates. It then runs `Render` to issue rendering-related commands.

During rendering, the main thread calls graphics APIs to set rendering states (Shader, texture, matrix, alpha blending, etc.) and then issues DrawCalls. All these graphics API calls interact with the driver layer, which maintains all rendering states. Such calls may trigger driver-side state changes and cause stuttering. Since driver states are transparent to upper-level calls, the occurrence and duration of stutters are unknown to the caller (CPU1). Meanwhile, other CPU cores may be idle, causing resource waste.

Therefore, the rendering part can be separated into an **independent render thread** running in parallel with the main thread to reduce main thread stalls.

The general workflow:

Graphics APIs called in the main thread are packaged as **commands** and submitted to a render queue, reducing the main thread’s graphics API overhead and improving frame rate.

The render thread fetches commands from the queue and executes graphics API calls to the driver. This interaction cost is moved from the main thread to the render thread.

Unity enables **Multithreaded Rendering** by default in Project Settings, and it is generally recommended to keep it enabled. However, GameOptim has found that some projects disable it.

When multithreaded rendering is **enabled**, CPU time waiting for GPU is mainly counted in **Gfx.WaitForPresent**.

When **disabled**, this cost is mainly counted in **Graphics.PresentAndSync**.

Thus, whether `Gfx.WaitForPresent` appears in the profile is a key indicator of whether multithreaded rendering is enabled.

Notably, during development and testing, you may temporarily disable multithreaded rendering to build and test, which more directly reflects rendering bottlenecks.

For projects with multithreaded rendering enabled normally, the trend of **Gfx.WaitForPresent** is highly meaningful.

Higher local GPU pressure leads to longer CPU waiting time and higher `Gfx.WaitForPresent` cost.

If `Gfx.WaitForPresent` lasts for **dozens or even hundreds of ms**, the corresponding scene is **GPU-bound**.

In addition, based on extensive project testing by GameOptim, excessive GPU pressure also increases the main rendering CPU functions:

**Camera.Render** and **RenderPipelineManager.DoRenderLoop_Internal**.

## 3.2.2 On-Screen Rendered Face Count

The two most basic factors affecting rendering efficiency are **Triangles** and **DrawCall**.

Generally, triangle count is **proportional** to GPU rendering time. For most projects, **opaque triangles** far outnumber transparent ones and require special attention.

GameOptim’s recommended triangle limits:

- Low-end devices (4GB RAM): **≤ 250,000 triangles** on screen
- High-end devices: **≤ 600,000 triangles**

If on-screen triangle count is too high, use **Frame Debugger** to analyze key rendered objects.

![53](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.2Render/53.png)

Common optimization methods:

- Strictly control mesh face count during production, especially character and terrain models. Watch for meshes over tens of thousands of faces.
- Use **LOD** to reduce on-screen faces: use low-poly models on low-end devices, cull unimportant small objects.

Important note:

The triangle count tracked by GameOptim is **not the original model face count**, but the **actual rendered face count** per frame. It depends on both model complexity and **rendering passes**, and more directly reflects rendering pressure.

For example:

A mesh of 10,000 faces with a Shader using **2 Passes**, or rendered by **2 cameras**, or with post-effects (SSAO, Reflection) will show **20,000 triangles**.

Such operations that **double the triangle count** must be strictly restricted on low-end devices and carefully balanced on high-end devices.

## 3.2.3 Batch (DrawCall)

In Unity, **DrawCall and Batch must be distinguished**.

One Batch may contain multiple DrawCalls. We usually care more about **Batch count**, as it is the actual unit that submits data to the GPU and the real target for optimization.

Four common batching methods:

**Dynamic Batching, Static Batching, SRP Batcher, GPU Instancing**.

Discussion of batching is complex and will not be expanded in detail here. Below is a brief summary of conditions, advantages, and disadvantages.

### (1) Static Batching

Conditions: Different meshes using the **same Material**.

Pros:

- Reduces vertex binding and geometry transfer

- Reduces material switching when adjacent materials are the same

  

  Cons:

- Offline merging may increase package size if meshes contain duplicate resources

- Runtime merging causes short CPU peaks when creating Combined Mesh

- May increase memory usage due to duplicated data

### (2) SRP Batcher

Conditions: Different meshes using the **same Shader and same variant**.

Pros:

- Reduces Uniform Buffer writes

- Pre-builds Uniform Buffer per Shader; no CPU write inside Batch

  

  Cons:

- Fixed Constant Buffer (CBuffer) GPU memory overhead

- **Does not support MaterialPropertyBlock**

### (3) GPU Instancing

Conditions: **Same mesh + same Material**.

Pros:

- Ideal for rendering many identical objects (monsters, props)

- Reduces animation module overhead while batching

  

  Cons:

- May cause negative optimization and increase DrawCalls

- Instancing order may be broken; manual grouping via API is sometimes needed

## 3.2.4 Particle System Rendering Overhead

Generally, `ParticleSystem.Draw` in the rendering callstack reflects the particle system DrawCall count during testing.

High particle DrawCalls lead to heavy transparent rendering overhead.

![54](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.2Render/54.png)

Common optimizations for particle DrawCalls:

(1) **Tiered particle culling**

Set **max active particle limits** per device tier, similar to MMO on-screen player limits.

Use a particle pool. Disable instantiation of non-player skill particles beyond a certain count. Set a max pool size per particle type to control total count.

(2) **Texture Sheet Animation (Sprites Mode)**

Use **TextureSheetAnimation** to reduce DrawCalls.

In Mode, select **Sprites** instead of regular grid frames.

Define a sprite list per particle. This supports:

- Sprite Packer (atlas merging)
- Custom pivot
- Per-sprite size

Sprite Packer enables **shared materials** across different particle systems, improving batching via **Dynamic Batching**.

(3) **Fix particle interleaving (major cause of high DrawCalls)**

Example:

One prefab with 5 particle systems (1‑5). 100 such prefabs in scene → 500 particles.

By default, rendering order becomes:

12345 12345 12345…

Result: **500 DrawCalls** instead of ideal **5**.

Solution:

Reorder rendering by adjusting:

**Render Queue, Sorting Layer, Order in Layer, Sorting Fudge**

This greatly improves particle batching and reduces Batch count.

(Actual method depends on particle production in the project.)



## 3.2.5 UGUI UI Rendering Overhead



In combat scenes, other modules already impose heavy time consumption, so the UI module must carefully control performance overhead. This includes not only UI update overhead but also rendering overhead. Generally, UI DrawCalls in combat scenes are best controlled at around **40–50**.

Without reducing UI elements, controlling DrawCalls essentially means maximizing UI batching. Normal batching requires the same material, but in UGUI, batching often fails even for elements using the same material and atlas. This is related to UGUI’s DrawCall calculation mechanism. Detailed principles can be found in *In-depth Explanation of UGUI DrawCall Calculation and Rebuild Optimization*.

During UGUI production, the following points are recommended:

(1) Only UI elements under the **same Canvas** can batch. Different Canvases do not batch even with the same Order in Layer, so reasonable UI structure and layout are critical.

(2) Integrate UI elements into **atlases** to ensure consistent material and atlas. Small UI elements such as buttons and icons can be fully atlas-packed. When they appear densely at the same time, DrawCalls are effectively reduced.

(3) Under the same Canvas with the same material and atlas, **avoid hierarchical interleaving**. Generally, UI elements eligible for batching should have the same “hierarchical depth”.

(4) Set **Pos Z** of related UI elements to **0** as much as possible. UI elements with non-zero Z can only batch with adjacent elements in the Hierarchy and easily break batching.

(5) For Image components with Alpha = 0, enable **Cull Transparent Mesh** on CanvasRenderer; otherwise, they still generate DrawCalls and break batching.

Additional rendering overhead comes from UI-induced GPU Overdraw, which is discussed in the final GPU chapter.



## 3.2.6 Shader.CreateGPUProgram



This API often appears in the main rendering callstack and causes **most CPU spikes in the rendering module**. It represents the time cost when a Shader is rendered for the first time, related to Shader complexity. It should be monitored if called during gameplay with high time spikes.

![55](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.2Render/55.png)

Solution:

Collect used Shader variants via **ShaderVariantCollection (SVC)** and package them into AssetBundles. After loading the SVC, call **ShaderVariantCollection.WarmUp()** during early game scenes to trigger `Shader.CreateGPUProgram` in advance and cache the SVC. This avoids runtime calls and local high CPU time.

However, projects that have done this still sometimes detect runtime spikes, indicating **missing variants**. Developers can use Profiler Timeline mode to identify which Shaders trigger the API. Reference: *An Idea for Shader Variant Collection and Build Optimization*.



## 3.2.7 Culling



In most cases, Culling itself is not time-consuming, but its cost reflects important rendering issues.

(1) **Large number of cameras**

High Culling time proportion in the main rendering stack (typically around 10%–20% in normal projects).

(2) **Too many small objects in the scene**

Culling time is highly correlated with the number of small GameObjects. It is recommended to optimize scene construction, reduce excessive small objects, and lower Culling overhead.

Use dynamic loading, block-based display, **Culling Group**, or **Culling Distance** to optimize.

(3) **Occlusion Culling**

Using multithreaded rendering + Occlusion Culling often increases worker-thread pressure and raises total Culling time.

Since Occlusion Culling computes occlusion relationships, it reduces rendering cost but introduces non-negligible overhead, **often unsuitable for most mobile scenes**.

It is recommended to disable Occlusion Culling partially for comparison before deciding whether to enable it.

(4) **Bounding Box Update**

**FinalizeUpdateRendererBoundingVolumes** in the Culling stack represents bounding box update time, common in **Skinned Mesh Renderers** and particle systems. Frequent calls indicate large numbers of Skinned Meshes or complex particle systems updating.

(5) **PostProcessLayer.OnPreCull**

This method is related to the PostProcessing Stack. Add a static variable `GlobalNeedUpdateSettings` in `PostProcessManager.cs`, set it to **true** only during scene switching to trigger `UpdateSettings`. This avoids per-frame updates and reduces overhead.

## 3.2.8 Shadows



Shadows are core rendering effects that enhance depth and realism, but mobile hardware has limited computing power. Unreasonable shadow settings can double on‑screen triangle count, surge GPU bandwidth usage, and increase CPU/GPU computation, becoming a major performance bottleneck. Therefore, mobile projects require shadow optimization based on **tiered strategy + precise control** to balance visual quality and performance.

Shadow performance cost affects both CPU and GPU, mainly in three stages:

(1) **CPU overhead**: Boundary calculation for casters (Shadowmap generation), frustum culling, multi-light shadow blending, and Shadowmap memory allocation.

(2) **GPU overhead**: Shadowmap rendering (additional full-screen draw), shadow sampling (increased texture bandwidth), shadow filtering (multi-sample for PCF soft shadows).

(3) **Resource overhead**: As a Render Texture, Shadowmap resolution directly determines memory usage. For example, a 1024×1024 RGBA32 Shadowmap occupies about 4 MB. With cascaded shadows, memory increases linearly with cascade count.

Common issues and key optimization strategies:

(1) **Tiered strategy**

Shadows are a key scenario for tiered optimization. Differentiated policies should be defined based on GPU performance and memory:

- **Low-end devices**: Disable all dynamic shadows, or keep only simple shadows for core objects (player). Use baked shadows or planar shadows. Prioritize frame rate over non-essential visuals.
- **Mid-end devices**: Use basic shadow settings, limit Shadowmap resolution, disable soft shadows, keep only main light shadows, and set **Shadow Distance to 20–30 m**.
- **High-end devices**: Use soft shadows and cascaded shadows cautiously with strict limits. Shadowmap resolution and distance may be increased moderately.

(2) **Control shadow casting and receiving range**

Not all objects need to cast or receive shadows. Precise filtering greatly reduces overhead:

- Disable shadows for non-critical objects: small props, decorative vegetation, distant objects, transparent objects (particles) by turning off **Cast Shadows** and **Receive Shadows** in Inspector.
- Use layer-based shadow control: Configure shadow interaction via **Project Settings → Graphics → Layer Collision Matrix** to reduce invalid computation.
- Dynamically adjust **Shadow Distance**: Shorten to 15 m in close combat, extend to 30 m in open world, avoiding wasted performance on distant shadows.

(3) **Optimize Shadowmap settings**

Shadowmap parameters directly determine performance. Key controls:

- **Resolution**: Mobile recommended ≤ 1024×1024, max ≤ 2048×2048.
- **Cascade count**: Unity cascades split the frustum into multiple parts, each with its own Shadowmap. Mobile recommended ≤ 2; low-end devices use 1.
- **Shadow filtering**: Soft shadows (e.g., PCF 4×4) cost 4–8× more than hard shadows. Hard shadows recommended for mid-low-end devices.
- **Light count**: Limit shadow-casting lights to ≤ 1 per scene. Keep only main light; disable shadows for point/spot lights or replace with baked shadows.

(4) **Baked shadows**

This is a classic example of **trading memory for performance**.

For static scenes (terrain, buildings, static decor), baked shadows are optimal for mobile: shadows are pre-baked into lightmaps with no real-time cost.

- Mark static objects with **Contribute GI** and **Receive GI**.
- Optimize lightmaps: lower resolution, use compressed formats to reduce memory.
- **Hybrid baking**: Static objects use baked shadows; dynamic objects (characters, monsters) use real-time shadows. Light Probes blend dynamic and baked shadows naturally.

(5) **Alternative technical solutions**

For scenes requiring dynamic shadows but limited hardware, use lightweight alternatives:

- **Planar Shadows**: Draw shadows only on ground planes using simple matrix math, no Shadowmap needed. Extremely low CPU/GPU cost, suitable for 2.5D games.
- **Low-poly shadow casters**: Create simplified meshes (1/5 faces of LOD 0) for shadow casting only, reducing triangle count without obvious quality loss.
- **Shadow distance fade**: Use Shader to make shadows fade out with distance, completely invisible at Shadow Distance boundary, eliminating useless distant rendering.

In summary, the core of mobile shadow optimization is **trade-off**:

Abandon non-essential shadows on low-end devices, replace high-cost real-time shadows with baked or low-cost alternatives. Many more methods are available based on project needs. The goal is to minimize performance overhead while maintaining acceptable visual quality.
