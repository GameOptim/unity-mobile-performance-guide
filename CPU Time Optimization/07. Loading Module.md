## 3.7.1 Shader Loading

### (1) Shader.Parse

`Shader.Parse` refers to the parsing operation during Shader loading. Frequent execution is usually caused by **duplicate Shader loading**, which has two meanings:

The first layer is **Shader redundancy**.

This usually occurs when Shaders are **passively included in multiple AssetBundles** without dependency packaging during AB build. When resources in these AssetBundles are loaded, the Shaders are loaded repeatedly, causing multiple `Shader.Parse` calls and **multiple copies of the same Shader in memory**.

The solution is simple: package all redundant Shaders into a **shared public AB**. Other AssetBundles using this Shader will only reference the shared AB, ensuring only one copy exists in memory and avoiding repeated parsing.

The second layer is **repeated load/unload without caching**.

Even if the Shader is packaged into a shared AB, if it is unloaded immediately after use without caching, it must be reloaded and re-parsed when needed again, causing repeated `Shader.Parse`.

Generally, custom Shaders after variant optimization have low memory usage and can be **loaded and cached uniformly at game startup**.

For Unity built-in Shaders with few variants, add them to **Always Included Shaders** in Project Settings to avoid redundancy and repeated parsing.

### (2) Shader.CreateGPUProgram

This API may also appear in the loading module, UI module, or logic callstack. The optimization method is the same as mentioned earlier and will not be repeated.

## 3.7.2 Resources.UnloadUnusedAssets

This API is automatically called by Unity during scene switching and usually has high single-call time cost. **Manual calling is not recommended** under normal circumstances.

However, in projects without scene switching or using **Additive scene loading**, this API is not triggered, leading to increasing resource count and memory. In this case, manual call every **5–10 minutes** is acceptable.

The underlying mechanism:

For each asset, Unity traverses all GameObject nodes in the Hierarchy and objects in managed memory to check usage. Only completely unused assets are unloaded.

In short, the time cost of `Resources.UnloadUnusedAssets` is roughly proportional to:

**(GameObject count + Mono object count) × Asset count**

Thus, it is extremely time-consuming. Recommendations:

(1) Use `Resources.UnloadAsset` / `AssetBundle.Unload(true)`

These high-efficiency APIs can unload confirmed unused assets at runtime, reducing pressure during unified unloading and shortening time during scene switching.

(2) Strictly control the number of **Materials and Particle Systems**

These two resource types usually do not consume the most memory but often reach thousands of instances, greatly increasing the cost of `Resources.UnloadUnusedAssets`.

(3) Reduce resident managed memory

Object count in the heap significantly affects unloading time, as discussed earlier.

## 3.7.3 AssetBundle Loading

AssetBundle is the most common resource loading method on mobile.

Best practice:

Use **LZ4 compression** and load via **LoadFromFile**.

Tests show that even large ABs (10×1024×1024 textures) take only **~0.x ms** to load.

Other methods are much slower:

- `LoadFromMemory`: dozens of ms
- `UnityWebRequest`: significantly higher resident memory

`LoadFromFile` efficiently loads uncompressed or LZ4 compressed ABs from local storage.

On consoles and mobile, only the AB header is loaded; data remains on disk and objects are loaded **on demand** (when `Load()` is called or InstanceID is referenced), with low memory overhead.

**Note**: In Editor, the entire AB is loaded into memory, which may cause temporary memory spikes. These spikes are **Editor-only** and should be retested on real devices.

This API only supports **uncompressed or LZ4** format.

LZMA compresses the entire package and cannot be read partially, so it does not support on-demand loading.

`LoadFromMemory` is **not recommended** for large-scale use due to high time cost and increased heap memory.

If encryption is required, only encrypt critical configs and code; textures and meshes do not need encryption, as low-level extraction tools already exist.

## 3.7.4 Resource Loading

With reasonable loading strategy, resource loading cost mainly occurs at startup and scene switching and usually does not cause severe bottlenecks.

Optimization rules:

- For assets with **single load time over hundreds of ms**, simplify asset complexity.
- For **frequently loaded assets**, cache after first load to avoid repeated overhead.

A common issue in Unity async loading:

The maximum per-frame loading time is limited, causing main thread idling. During scene switching, async loading may take a long time due to low budget.

The API **`Application.backgroundLoadingPriority`** defaults to **BelowNormal** (max 4 ms per frame).

It is strongly recommended to set it to **High** (max 50 ms per frame) to speed up loading.

## 3.7.5 Instantiation and Destruction

Problems include:

- **Single instantiation too slow**
- **Frequent repeated instantiation**

Solutions:

- For high-cost assets: simplify or use **frame-split instantiation** (load key UI first, decorations later).
- For frequently used assets: use **object pooling** with active/inactive instead of repeated `Instantiate`/`Destroy`.

## 3.7.6 Activation and Deactivation

The time cost of `SetActive` is low individually but significant with **extremely high calls per frame**.

Many projects have excessive `SetActive` calls due to unreasonable logic, often with far more `SetActive(true)` than `SetActive(false)` or vice versa, including many unnecessary calls.

Since `SetActive` involves **cross-domain calls between C# and Native**, high frequency introduces noticeable overhead.

Solution:

Add a **state cache** in logic. Check the current active state **before calling SetActive** to avoid redundant API calls, replacing native overhead with lighter logic overhead.
