## 3.1 Overview

### 3.1.1 Module Division

GameOptim categorizes functions with clear CPU responsibilities and typically high time consumption into modules including: Rendering, UI, Physics, Animation, Particle, Loading, Logic, etc.

This does not mean modules are completely independent. For example, rendering performance is inevitably affected by complex UI and particle effects, and many loading operations are actually invoked and executed within game logic.

Module division helps us identify problems and focus on key points. At the same time, we must understand the relationships between modules to solve problems more efficiently.

### 3.1.2 Time Consumption Bottleneck

When a project suffers from low frame rate and obvious stuttering due to CPU bottlenecks, it is critical to identify which module and which issue is the main cause.

Although we have organized the main engine modules, problems in each module vary widely and cannot be generalized, and their contributions to CPU pressure also differ. We need an accurate understanding of what time consumption can be regarded as a potential performance bottleneck.

For mobile projects, the CPU optimization goal is to achieve a stable 30 FPS on mid-to-low-end devices most of the time.

To meet this target, simple calculation shows that average CPU time per frame should be controlled below 33 ms.

However, an average below 33 ms does not mean CPU time is well optimized.

Performance pressure varies during runtime:

- Very low pressure in UI scenes
- Very low frame rate in core combat scenes
- Occasional long freezes of hundreds of milliseconds or even seconds

Yet the overall average may still remain below 33 ms.

Therefore, GameOptim defines the following standard:

In one test, if frames with CPU time ≥ 33 ms account for less than 10% of total frames, the project’s CPU performance is considered within normal range.

The higher this percentage, the more severe the CPU bottleneck.

The above discussion focuses on macro CPU optimization goals.

Similar to memory optimization, we still need to combine detailed data of specific modules to diagnose and solve actual problems in the project.
