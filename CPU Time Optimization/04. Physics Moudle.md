# 3.4 Physics Module

For more comprehensive content related to physics module optimization, please refer to *Unity Performance Optimization — Physics Module*.



## 3.4.1 Auto Simulation

Since Unity 2017.4, **Auto Simulation** has been exposed and enabled by default, meaning physics simulation runs continuously throughout the project. However, this time cost is often wasted in some scenarios.

A key criterion for judging wasted physics time is the **Contacts count** — the number of collision pairs at runtime. Generally, the more collision pairs, the higher the CPU cost of the physics system. Yet in many mobile projects, we detect that the Contacts count remains **0** during the entire game.

In this case, developers can disable Auto Simulation for testing. If disabling it does not affect game logic (dialogue, combat, etc.), this overhead can be fully saved.

Note: If raycasts are required, **Auto Sync Transforms** must be enabled after disabling Auto Simulation to ensure raycasts work correctly.

## 3.4.2 Contacts

As mentioned above, if Contacts count is always 0, the project likely does not need real physics simulation, and it can be disabled.

When physics is actually used, the CPU cost increases with the number of collision pairs. Therefore, **strictly controlling Contacts count** is critical for reducing physics overhead.

In the physics module of GOT Online Overview, the number of Overlap events is recorded, which essentially represents the Contacts collision count.

![64](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.4Physics/64.png)

Many projects contain unnecessary **Rigidbody** components that cause unintended collisions and wasted overhead. In addition, you can check and modify the **Layer Collision Matrix** in Project Settings → Physics, disable collision detection between unnecessary layers, and minimize the Contacts count.

The report also provides curves for Rigidbody count and static collider count to help developers judge performance issues caused by physics setup.



## 3.4.3 OnTrigger Replacement

Another common use of physics is trigger callbacks (such as **OnTrigger**, **OnCollision**). However, in most cases — such as character position checking, interaction detection, etc. — these can be replaced by other methods, including **Bounds.Contains**, **Physics.OverlapSphere**, and similar APIs.

These APIs perform simple geometric calculations to determine whether a point lies inside a bounding box, **without requiring full physics simulation**. After full replacement, Auto Simulation can also be disabled.

## 3.4.4 Colliders

Besides the number of colliders, **collider complexity** also affects physics module time consumption.

By default, the collider generated for a model is a **MeshCollider** that closely matches the original mesh. However, high-precision MeshColliders are often unnecessary, even in competitive shooting games with strict hit detection requirements.

In most projects, using complex MeshColliders provides no practical difference for logic detection, but introduces extremely high additional overhead.

Therefore, **MeshColliders should be avoided as much as possible** and replaced with simple colliders. Even combining multiple simple colliders is far more efficient than a complex MeshCollider.

MeshColliders perform triangle-based collision detection: the more triangles, the higher the computational cost.

Simple colliders such as **Sphere, Box, Capsule** have basic shapes, and Unity uses faster geometric algorithms for collision calculations.

MeshColliders also consume more memory. Simple colliders have high reusability, so only a few small primitive colliders exist in memory.

## 3.4.5 Physics Update Count

The main time-consuming function of Unity physics simulation runs in **FixedUpdate**.

In other words, the more times this function is called per frame, the more frequent physics updates are, and the higher the CPU cost per frame.

The physics update count (FixedUpdate calls per frame) depends on two settings in **Project Settings → Time**:

**Fixed Timestep** and **Maximum Allowed Timestep**.

A key characteristic of the physics system:

when the previous frame is delayed, Unity calls **FixedUpdate.PhysicsFixedUpdate repeatedly** early in the current frame.

**Maximum Allowed Timestep** limits the number of physics updates per frame. The smaller the value, the fewer physics calls per frame.

Example:

Fixed Timestep = 20 ms, Maximum Allowed Timestep = 100 ms.

- A 30 ms frame → 1 physics update
- A 200 ms frame → 5 physics updates

![66](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.4Physics/66.png)

An effective optimization is to **adjust these two parameters**, especially **lower the maximum update count** (default: 17, recommended ≤ 5). This prevents excessive physics time.

On the other hand, optimizing CPU time in other modules reduces long frames, so FixedUpdate will less often hit the maximum count.

The same logic applies to all functions in FixedUpdate.

For this reason, **placing excessive game logic in FixedUpdate is not recommended**.
