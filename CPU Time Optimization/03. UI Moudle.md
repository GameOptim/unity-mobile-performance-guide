# 3.3 UI Module

In Unity, the mainstream UI frameworks include UGUI, NGUI, and the increasingly popular FairyGUI. This document focuses on **UGUI**, the most widely used. For more comprehensive UGUI-related optimization, please refer to *Unity Performance Optimization — UI Module*.

## 3.3.1 UGUI EventSystem.Update

The `EventSystem.Update` function represents the time cost of the UGUI event system. High consumption mainly relates to the following two factors:

(1) **High trigger callback cost**

As the main function of the UGUI event system, it is mainly triggered on touch release. High CPU overhead usually comes from other time-consuming functions called inside it.

Further detection should be performed using `Profiler.BeginSample`/`EndSample` markers or GOT Online with API markers to locate the specific sub-function or code segment causing high cost.

![57](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.3UI/57.png)

(2) **High polling cost**

All UGUI components have **Raycast Target** enabled by default, preparing them for event response.

In practice, most UI components such as Image and Text do not respond to events but still participate in raycast polling during touch or hover, causing unnecessary overhead.

Especially when there are many UI components, **disabling Raycast Target for non-interactive components** can effectively reduce `EventSystem.Update()` time.

![58](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.3UI/58.png)

## 3.3.2 UGUI Canvas.SendWillRenderCanvases

The time cost of `Canvas.SendWillRenderCanvases` represents **UI element self-update**, which must be distinguished from mesh reconstruction cost in `Canvas.BuildBatch` (see below).

![1](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/1.png)

Sustained high cost is usually caused by overly complex UI elements with extremely frequent updates.

Self-updates include: image replacement, text or color changes, etc.

Position, rotation, or scale changes do **not** produce overhead in this function.

The cost depends on the **number of updated UI elements** and their **complexity**. Optimization can be done from the following aspects:

(1) **Reduce update frequency of frequently refreshed UI elements**

For example: minimap icons, character/monster HP bars — update only when values change beyond a threshold.

Skill cooldowns, damage text — use **frame-skipping updates**.

To locate frequently updating elements, it is recommended to **inject probes into the source code of Canvas.SendWillRenderCanvases** to output updating elements at runtime.

Reference: MOMO’s blog *UGUI Research: Find the exact UI element causing mesh reconstruction*.

(2) **Avoid updating complex UI elements**

Complex elements include:

- Text with many strings, Rich Text, Outline, or Shadow effects
- Image with Type set to Tiled

These have extremely high vertex counts and cause heavy overhead once updated.

For frequently changing effects (e.g., floating damage text) that require Outline or Shadow, use **fixed art font** to avoid multiplying vertex count.

UI complexity can be judged by **UI Vertex count**.

The built-in Unity Profiler UI module shows the number of UI elements and vertices under each Canvas per batch, allowing quick location of complex elements.

![59](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.3UI/59.png)

(3) **Pay attention to Font.CacheFontForText**

This function often causes **time spikes**.

It mainly generates the dynamic font **Font Texture**. Sudden high runtime cost is usually caused by writing many new characters at once, leading to **Font Texture expansion**.

Optimization:

- Reduce font types and font sizes
- Pre-display commonly used characters to expand Font Texture in advance

![2](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/2.png)

(4) **Projects using TextMeshPro (TMP)**

Large amounts of text (cutscenes, chat) may cause sustained high cost or stutters in `Canvas.SendWillRenderCanvases`, often with `TMP.Generate` in the callstack.

This is because TMP incurs high cost when frequently adding new characters to the dynamic font atlas.

GameOptim tests show that switching to **static TMP font** can reduce UI time by nearly 50%.

Thus, the TMP static atlas method discussed in the memory chapter also significantly improves time cost.

(5) **Projects using UI Particle**

Most projects using UI Particle extensively suffer from poor performance.

UI Particle inherits from UGUI’s `MaskableGraphic`, so it has both **particle update overhead** and **UGUI element update overhead**.

Its vertices are usually complex and updated very frequently, leading to extremely high cost.

It is generally recommended to **minimize usage, simplify effects, or use alternative solutions**.



## 3.3.3 UGUI Canvas.BuildBatch

`Canvas.BuildBatch` is called when the merged UI mesh needs to be modified.

Generally, the previously mentioned `Canvas.SendWillRenderCanvases()` will trigger `Canvas.BuildBatch`.

In addition, movement of UI elements inside a Canvas will also trigger `Canvas.BuildBatch`.

![3](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/3.png)

`Canvas.BuildBatch` initiates UI mesh merging on the main thread; the actual merging is processed in worker threads.

When worker threads are overloaded or the merged UI mesh is excessively complex, the main thread will stall, and the waiting time is recorded in **EmitWorldScreenspaceCameraGeometry**.

High time consumption in these two functions indicates that the rebuilt Canvas is very complex.

In this case, the Canvas should be **split into smaller Canvases**:

place static elements in one Canvas and dynamic updating elements in another.

The static Canvas will not update its mesh due to caching, thus reducing mesh update complexity and rebuilding time.

## 3.3.4 UGUI CanvasRenderer.SyncTransform

It is common to see frequent calls of `CanvasRenderer.SyncTransform` in some projects.

In the example, the call count reaches **1017** in a single frame.

Extremely frequent calls of `Canvas.SyncTransform` will cause its parent node **UGUI.Rendering.UpdateBathes** to become very time-consuming.

![4](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/UI_Module/4.png)

When the call count is excessively high, consider the following four causes and apply corresponding strategies to reduce calls and overhead:

1. Any Transform change (position, rotation, scale, e.g., floating text animations) triggers `CanvasRenderer.SyncTransform`.

   Many simultaneous Transform changes (e.g., moving player HUDs, bouncing damage text) lead to high call counts.

   In such cases, **reduce update frequency** appropriately.

   

2. Calling `SetActive(true)` triggers `CanvasRenderer.SyncTransform` on **all UI elements in the current Canvas and its parent Canvases**.

   Notably, `SetActive(false)` does **not** trigger it.

   Therefore, **separate frequently activated/hidden UI elements from static elements**.

   

3. `Instantiate` of a UI element triggers `CanvasRenderer.SyncTransform` on all elements in the current Canvas and its parent Canvases.

   

4. `Destroy` of a UI element triggers `CanvasRenderer.SyncTransform` on all elements in the current Canvas only.

   

Combining 3 and 4: **separate frequently instantiated/destroyed UI elements from static elements**.

PS: If the API has no actual effect (e.g., calling `SetActive(true)` on an already active object), `CanvasRenderer.SyncTransform` is **not** triggered.

## 3.3.5 UI Scene Switch Stutter

Long UI switch time is a common pain point for developers.

From the player’s perspective, large visual changes during UI switching mean that delays **below 200 ms** usually do not cause obvious stutters.

However, in practice, complex UIs such as Battle Pass, Backpack, and Character Showcase often take **over 200 ms or even 1 second** to switch, causing obvious interruption and poor experience.

Most UI switch time comes from **UI instantiation, active state switching, and related logic cost**, which are not strictly counted as UI module functions.

However, the following strategies can greatly alleviate these issues:

1. **UI classification and caching**

   Cache frequently used UI interfaces (e.g., character page in a gacha game, shop in MOBA).

   Which UIs to cache depends on game type and hot-spot statistics.

   

2. **Frame-split loading**

   Many UIs (Backpack, Battle Pass) open slowly due to massive icons.

   By prioritizing UI elements:

   load buttons, key values, and item names first;

   decorations, icons, and tab content can be loaded in subsequent frames.

   

This makes the UI respond **immediately** when clicked, with important content interactive instantly, greatly improving user experience.
