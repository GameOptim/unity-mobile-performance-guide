# 3.6 Particle System

For more comprehensive content on particle system optimization, please refer to *Unity Performance Optimization — Partical System*.



## 3.6.1 Number of Playing Particle Systems

GameOptim counts the total number of particle systems and the number of **Playing** particle systems.

The former refers to the total number of ParticleSystems in memory, including both playing and those in the object pool.

The latter refers to the number of **active playing ParticleSystem components**, both on-screen and off-screen.

We recommend the peak count per frame be **no more than 50** on 1GB RAM devices.

![70](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.6Particle/70.png)

For these two values:

- Check whether the **total particle system peak count** is too high. Select a peak frame to see which particle systems are cached, whether they are reasonable, and whether over-caching exists.
- Check whether the **Playing peak count** is too high. Select a peak frame to see which particle systems are playing and whether they are reasonable.

Setting a **maximum limit for the same type of particle**, as mentioned earlier, is also a common solution.

**Tiered configuration** is also essential in particle system optimization.

For example, a flame effect prefab with 5 sub-particles (1,2,3,4,5):

3,4,5 may be sparks, smoke, and heat haze added by artists, while only 1 and 2 are the main flame body.

On low-end devices, only 1 and 2 should be kept.

Although we mostly discuss particle **rendering overhead** (both CPU and GPU) when talking about performance,

in projects with heavy particle usage and extremely high counts, excessive **Playing particles** will also significantly increase the CPU cost of **ParticleSystem.Update()**.

## 3.6.2 Culling Mode

Setting a reasonable **Culling Mode** for particle systems is an effective way to reduce CPU update overhead.

![71](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.6Particle/71.png)



![72](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.6Particle/72.png)

The key settings are **Simulation Space** and **Culling Mode** as shown above.

- Simulation Space options: Local, World, Custom
- Culling Mode options: Automatic, Pause And Catch-up, Pause, Always Simulate

Default settings for newly created particles: **Local + Automatic**.

We naturally want to **stop computation when particles are off-screen** to reduce overhead.

We tested **ParticleSystem.Update()** cost when particles are off-screen under different combinations. Results:

(1) In Local mode, only **Always Simulate** causes update cost (no extra modules enabled).

(2) In Local mode, if modules such as Collision are enabled, **Automatic** still causes cost.

(3) In Local mode, if Culling Mode is **Pause or Pause And Catch-up**, no cost occurs even with Collision.

(4) In World mode, **Automatic** still causes cost (no extra modules enabled).

(5) In World mode, **Pause** results in no cost even with Collision.

In summary, the ability of Culling Mode to restrict overhead increases progressively.

Therefore:

- Set Culling Mode to at least **Automatic**.
- Use particles with **Simulation Space = World** with caution.
- Use heavy modules such as Collision, Trigger, Noise, Trails with caution.
- For particles requiring such modules, set Culling Mode to **Pause** to save CPU time.

## 3.6.3 Prewarm

**ParticleSystem.Prewarm** is a core initialization option.

Its original purpose is to simulate a full particle lifetime immediately when instantiated or activated from Deactivated state, so the effect appears **mature and fully formed** (e.g., steady fire, looping aura) from the first frame, avoiding a “growing from nothing” appearance.

However, this mechanism introduces significant **performance risks** — especially with many complex particles.

The instantaneous computation triggered by Prewarm often causes **CPU spikes and stutters**.

Main optimization methods:

(1) Reduce particle system complexity to lower the calculation amount during Prewarm.

(2) Avoid **simultaneous Prewarm activation**. Spread the load by activating particles **frame-split, delayed, or via cached reuse**.
