# 3.8 Logic Code

CPU time optimization of logic code highly depends on actual project requirements and programmers’ coding practice, making it difficult to discuss quantitatively. However, the GameOptim SDK provides convenient profiling APIs for logic code and GOT Online visualization, allowing developers to split complex functions, inspect stack time costs in reports, and verify optimization effects more efficiently.

We have seen an increasing number of teams use **JobSystem** to move part of logic code from the main thread to worker threads. For parallelizable logic, running tasks in worker threads is **highly recommended**, as it effectively reduces main thread CPU pressure.

# 3.9 Lua

GOT Online Lua mode provides a highly visual tool for analyzing CPU overhead caused by Lua, with clear call stacks and a unique reverse call analysis feature. The following uses a Lua report demo to briefly introduce how to analyze Lua performance with this tool.

**Important note**:

Function names in Lua reports follow the format:

**FunctionName@FileName:LineNumber**

You can locate high-cost functions and CPU spikes using the file name, line number, and function name.

For a function formatted as **X@Y:Z**:

- X: function name (unknown if unavailable)
- Y: file where the function is defined
- Z: line number where the function is defined

Note: When Lua runs as bytecode, Z is always **0**. Therefore, **using Lua source code during testing is strongly recommended**.

**Indicator definitions**:

- **Total %**: total time of current function / total time of root function (100%)
- **Self %**: self time of current function / total time of root function (100%)
- **Total Time**: total execution time in the range
- **Self Time**: total time minus child function time
- **Calls**: number of invocations
- **Avg Time**: Total Time / Calls
- **Significant Frames**: number of frames where self time > 3ms

**Function XXXX Stack Info (List)**:

Indicators are redefined (different from forward):

- **Self %**: self time of the target function in this call path / total self time of the target function (100%)
- **Self Time**: total self time of the target function in this path
- **Calls**: number of times this path was invoked
- **Avg Time**: average time per call in this path

After locating functions with high self time, common optimizations:

- Optimize the function body to reduce self time
- Identify frequently called paths and reduce call count

## (5) Optimization Suggestions

① Optimize the body of functions with **extremely high per-call time** to reduce self time.

② Locate frequently called paths and **reduce call frequency**.

③ For high-frequency functions, pay special attention to **massive Lua–C# cross-language calls**, which are inefficient and often cause high power consumption and overheating.

④ Lua function time in GameOptim reports includes time spent in **called C# functions**.

Therefore, Lua–C# interaction must be carefully reviewed.

For fixed logic that calls the same or multiple C# functions repeatedly, move the entire logic to the **C# layer** and expose only necessary parameters.

This reduces cross-language calls drastically and saves significant overhead.



# 3.10 ILRuntime

ILRuntime is less commonly used, but some teams still adopt it extensively in mobile projects due to legacy project habits.

However, based on GameOptim experience, projects using ILRuntime generally show poor performance in both **logic time consumption** and **heap memory usage**. Therefore, **avoiding or minimizing ILRuntime usage is strongly recommended**.

For hot-update solutions, **Lua** (widely adopted) or **HybridCLR (Huatuo)** (rapidly rising in usage) are much better alternatives purely from a performance perspective.

Below are practical optimizations for projects already facing ILRuntime-related performance issues but unable to switch solutions in the short term.

## CPU Level:

(1) Minimize ILRuntime usage in **core combat logic**; implement such logic in pure static C#.

Heavy computation or frequent loops inside ILRuntime will cause severe performance degradation.

ILRuntime may be used for lightweight tasks such as UI updates, but **must be avoided in core combat**.

(2) Build DLLs in **Release mode**.

(3) For Android, build using **Mono scripting runtime** and load via reflection. This can achieve performance close to native C#.

## Heap Memory Level:

(1) Reduce usage, especially in core combat, since ILRuntime causes **boxing** even for value-type variables.

(2) Disable debug macros to reduce heap allocation.

Define **DISABLE_ILRUNTIME_DEBUG** in PlayerSettings.

https://ourpalm.github.io/ILRuntime/public/v1/guide/FastQA.html
