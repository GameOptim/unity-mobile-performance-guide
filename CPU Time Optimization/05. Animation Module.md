For a more comprehensive discussion on animation-related optimizations, please refer to *Unity Performance Optimization — Animation Module*.



#### 3.5.1 Mecanim Animation System

The **Mecanim animation system** is Unity’s modern animation framework introduced after Unity 4.0, where animations are controlled via the `Animator` component. Compared with the legacy `Animation` system, Mecanim provides several notable advantages in terms of functionality:

1. A dedicated workflow for humanoid characters, including Avatar creation and muscle configuration;
2. Support for **animation retargeting**, allowing animations to be easily reused across different character models;
3. A visual **Animator editor**, enabling quick previewing and creation of animation clips;
4. More convenient construction of state machines and transitions between animation states;
5. Easy-to-use **Blend Tree** functionality.

From a performance perspective, for **skeletal animations with complex curves**, the Animator system generally performs better than the legacy Animation system. This is because Animator supports multi-threaded computation and can be further optimized by enabling **Optimized GameObjects**. 

Conversely, for very simple animations—such as basic translation or rotation—using the legacy Animation system can be more efficient than Animator.

 

#### 3.5.2 BakeMesh

For objects with relatively low polygon counts (e.g., 1–2k triangles) and short animation durations—such as minions in MOBA or SLG games—the `SkinnedMeshRenderer.BakeMesh` approach can be considered. This technique trades memory usage for reduced CPU cost.

The core idea is to **bake a skinned animation at specific time points into non-skinned meshes**, effectively converting an animation clip into a sequence of mesh frames based on a custom sampling interval. During playback, the system only needs to assign the nearest baked mesh frame, eliminating bone updates and skinning calculations (there is almost no animation computation involved—only mesh assignment).

This approach is particularly suitable for low-polygon characters, as it removes the runtime cost of skinning. Its benefit lies in exchanging memory for computation time, and the performance gains are especially noticeable when many instances of the same animated model appear simultaneously in a scene.

However, this method has clear limitations:

- Memory usage is heavily affected by vertex count, animation duration, and sampling interval;
- Baking itself is time-consuming and typically must be completed during scene loading.

Therefore, this technique is only suitable for models with **low vertex counts and short animation clips**.

 

#### 3.5.3 Number of Active Animators

The number of **active Animators** has a significant impact on animation-related CPU cost and is one of the most important quantifiable metrics when optimizing the animation module. Keeping this number within a reasonable range is a key optimization strategy, and developers should always validate whether the count aligns with what is actually visible on screen.

![](https://uwa-ducument-img.oss-cn-beijing.aliyuncs.com/GameOptim/3.5Animation/68.png)

1. Animator Culling Mode

One effective way to control the number of active Animators is to properly configure `Animator.CullingMode`. There are three available options:

- **AlwaysAnimate**The default setting. The Animator continues updating regardless of whether the object is within the camera frustum or has been culled by LOD.UI animations must use this mode; otherwise, visual issues may occur.
- **CullUpdateTransforms**When the object is outside the camera frustum or culled by LOD, the animation logic (state machine, transitions, conditions) continues to update, but visual-layer updates—such as retargeting, IK, and Transform data sent back from C++—are skipped.Setting some Animators to this mode can significantly reduce animation overhead for invisible objects without affecting gameplay logic.
- **CullComplete**Completely stops all animation updates. This mode is suitable for less important animation effects, especially on low-end devices, where visual presence may be kept while motion is frozen as part of a quality-scaling strategy.
- DOTween Plugin

In many cases, UI animations contribute a large number of active Animators. For simple UI animations—such as color changes, scaling, or movement—GameOptim recommends using **DOTween** instead. Testing has shown that DOTween generally delivers much better performance than native UI animations driven by Animators.

 

#### 3.5.4 Number of Animators with Apply Root Motion Enabled

In the `Animators.Update` call stack, a high proportion of `Animator.ApplyBuiltinRootMotion` often indicates that many model animations have **Apply Root Motion** enabled.

If an animation does not actually need to produce positional movement, this option should be disabled to avoid unnecessary computation.

#### 3.5.5 Animator.Initialize

The `Animator.Initialize` API is triggered when a GameObject containing an Animator component is **activated** or **instantiated**, and it can be relatively expensive.

Therefore, especially in combat scenarios, it is not recommended to frequently activate/deactivate GameObjects with Animators. For characters that are instantiated frequently, object pooling should be considered. When hiding a character, instead of deactivating the GameObject, developers can disable the Animator component and move the GameObject off-screen.

 

#### 3.5.6 MeshSkinning.Update and Animators.WriteJob

Mesh resources have a substantial impact on animation-related performance.

On one hand, high `MeshSkinning.Update` cost is usually caused by **large bone counts** and **high polygon counts** in skinned meshes. Mesh simplification and LOD grading are effective countermeasures.

On the other hand, under default settings, many projects keep bone node Transforms active in the scene. After their Transforms are computed on the native side, the data is sent back to the C# layer, introducing additional overhead.

When many characters are present, this bone Transform feedback becomes costly and is reflected in the `Animators.WriteJob` sub-function under `PreLateUpdate.DirectorUpdateAnimationEnd`.

To mitigate this, developers can enable **Optimize Game Objects** in the Rig tab of FBX assets, effectively “hiding” bone nodes and reducing Transform feedback overhead.

 

#### 3.5.7 GPU Skinning / Compute Skinning

Unity’s built-in **GPU Skinning** (referred to as **Compute Skinning** in newer versions) theoretically alters mesh and animation update paths to optimize skeletal animation processing.

However, based on extensive testing on mobile platforms—both iOS and Android—the performance gains provided by GPU Skinning across multiple Unity versions are often negligible, and in some cases even negative. Although Unity has gradually optimized this feature and moved related operations to the render thread, its practical effectiveness still requires further validation.

For scenarios involving large numbers of identical enemies, developers may consider implementing their own GPU skinning solutions combined with **GPU Instancing**. This approach can both reduce `Animator.Update` cost and achieve effective batching.

 

#### 3.5.8 Spine

Spine is a widely used animation solution in mobile games, but its performance characteristics are relatively average and can sometimes lead to unexpectedly high overhead.

At runtime, Spine’s CPU cost mainly appears in:

- `SkeletonAnimation.Update` and `SkeletonAnimation.LateUpdate`, or
- `SkeletonGraphic.Update` and `SkeletonGraphic.LateUpdate` (for UI-based Spine components).

The former applies to standard Spine components, while the latter applies to UI Spine components. Since Spine is a complex animation system with frequent updates, using Spine in UI can introduce additional overhead. Whenever possible, effects that can be implemented with standard components should avoid using UI Spine.

High Spine cost is usually caused by both **high per-call execution time** and **high call frequency**, which are influenced by the complexity of art assets and the number of Spine components playing simultaneously at runtime. Spine can also impact rendering pressure and heap memory usage.

Below are common Spine performance issues and corresponding optimization strategies:

1. **Spine asset creation**Complex timelines and excessive bones increase runtime cost. Artists should clean unused timelines, remove unnecessary bones and slots, use Spine’s built-in *Clear* functionality for each animation, and minimize the use of clipping.Spine assets should always be exported in **binary format**, which performs significantly better than JSON in both CPU time and heap memory usage.
2. **Number of Spine components**Monitor and limit the number of Spine components actively updating, especially in high-pressure scenes. Simple animations should avoid Spine whenever possible.
3. **Update When Invisible**Similar to Animator’s culling modes, `SkeletonAnimation` provides *Advanced → Update When Invisible*. Setting this option to *Nothing* stops updates for off-screen Spine animations, significantly reducing overhead.`SkeletonGraphic` also supports this setting, but it requires a parent `RectMask2D` to take effect.
4. **Freezing**`SkeletonGraphic` includes a *Freeze* option. When enabled, update logic returns immediately, producing no overhead while keeping the animation static. This is ideal for Spine animations that are only triggered under specific conditions.Although `SkeletonAnimation` does not provide this option by default, similar behavior can be implemented by modifying Spine’s runtime source code.
5. **Batching via SRP Batcher**By replacing Spine shaders with versions that support the SRP Batcher (available from the official Spine website), Spine animations in URP projects can benefit from SRP Batcher batching, significantly reducing rendering overhead.
6. **Overdraw**Spine animations are typically rendered as transparent objects. Complex setups can easily cause excessive overdraw, placing heavy pressure on the GPU. This must be addressed during the art production stage.
7. **On-demand loading to reduce heap usage**As projects evolve, some characters’ Spine assets may accumulate large numbers of skins and animations. Loading all of this data at once can severely increase heap memory usage and loading time.While splitting assets can alleviate the issue, it increases export complexity and maintenance cost. An alternative approach is **on-demand loading**, where only the required data is loaded into memory at runtime.
